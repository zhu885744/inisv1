# 用户 @ 提及（@用户）

在**文章、动态、独立页、评论**四处正文里可以 @ 用户。被 @ 的人会收到站内通知，
点内容里的昵称跳到对应作者的个人主页。

## 一条核心限制

> **可以 @ 的人，仅限「当前用户已关注的人」。**

这条限制在前端与后端都成立：

| 位置 | 行为 |
| :--- | :--- |
| 前端候选面板 | 只请求并展示关注列表（未关注的人根本不出现在候选里） |
| 后端保存内容 | 只把"已关注的昵称"规范化成链接，其余 `@xxx` 原样当普通文本，**不转链接也不发通知** |

所以即使有人手动输入 `@某某`（自己没关注），也不会产生链接与通知 —— 不能靠改前端绕过。
候选列表接口：`GET /api/mention/candidates`（`type=login`，登录即可用，只返回自己的关注对象）。

## 存储格式

保存时后端把 `@昵称` 规范化成 markdown 链接：

```
用户输入：@张三 你好
落库内容：@[张三](/author/12) 你好
```

为什么存链接而不是存原始文本：

- **文章 / 独立页**走 markdown-it，链接是原生语法，直接渲染成 `<a>`（`html: false` 下 HTML 会被转义，
  所以不能存 HTML 标签）；链接外保留 `@`，显示效果就是 `@张三`；
- **评论 / 动态**走 `Mellow/src/utils/emoji.js` 的 `renderEmojiWithBreaks`，其中 `renderMention()`
  把同一格式转成 `<a class="mention">`，四处表现一致；
- 昵称与 id 一起落库，**昵称后来改了也不会让链接失效**（显示的是当时的昵称）。

规范化是**幂等**的：`@[昵称](/author/1)` 不会被二次匹配（`@` 后面是 `[` 而不是昵称），
所以草稿反复保存、发布后再次编辑都不会重复处理。

## 匹配规则（`app/model/mention.go`）

| 规则 | 说明 |
| :--- | :--- |
| 只匹配已关注的人 | 昵称大小写不敏感；昵称不唯一时取 id 小者（结果确定，不会随机） |
| 最长匹配 | 从 `@` 之后取最长的命中昵称。中文昵称后面通常不带空格，不能用右侧边界判定：`@张三你好` 在存在昵称「张三你好」时匹配整串，否则退化为匹配「张三」 |
| 左侧边界 | `@` 左侧是字母 / 数字 / `.` `_` `-` `+` `%` 时不算提及 —— 邮箱 `a@b.com` 不会被误伤 |
| 昵称清洗 | 昵称里的 `[ ] ( ) |` 会破坏 markdown 链接语法，写链接时去掉（仅显示名，匹配仍按原昵称） |
| 不通知自己 | @ 自己会照常生成链接，但不发通知 |

## 通知

| 项 | 值 |
| :--- | :--- |
| 类型 | `type = mention`（`model.NotificationTypeMention`） |
| 标题 | `「触发人昵称」在评论/动态/文章/页面中提到了你` |
| 内容 | 正文摘要（链接还原成 `@昵称`，压掉换行，截断 120 字） |
| 跳转 | `bind_type` + `bind_id` 指向被 @ 的**内容**（评论指向它所在的文章 / 动态 / 页面），沿用站内信既有约定 |

**什么时候发**（避免打扰与重复）：

> 共同原则：**内容不可展示时一律不发** —— 待审核的文章 / 动态 / 页面 / 评论点进去看不到，
> 通知过去只会让人困惑；改在**审核通过的那一刻补发**。

| 场景 | 行为 |
| :--- | :--- |
| 创建时即已通过审核 | 保存即发（文章 / 动态 / 独立页 / 评论都适用；草稿与待审核不发） |
| **待审核 → 审核通过** | **补发全部**被 @ 用户。文章 / 独立页走 `notifyAuditChange`；动态走 `notifyMomentsAudit`；评论走后台「通过」按钮那条 `comment.update` 路径 |
| 首次发布（原为草稿） | 通知正文里的**全部**被 @ 用户（草稿阶段从未通知过，不能漏） |
| 已通过审核的内容再次编辑 | **只通知本次新增**的被 @ 用户（与旧正文比对），不反复打扰同一个人 |
| 独立页 | 没有草稿态：新建时全量通知，编辑时只通知新增 |

补发的实现入口：`model.NotifyMentionsOnApprove(kind, bindId, ownerUid)`（文章 / 页面 / 动态）与
`model.NotifyMentionsOnCommentApprove(commentId)`（评论）。

> ⚠️ **审核开关是个陷阱**：`contentAuditSwitch()` 在配置缺失时**默认返回 true（开启审核）**，
> 所以默认情况下新发布的文章 / 动态都会先进入待审核 —— 如果"审核通过"这一步没有补发逻辑，
> @ 通知就会永久丢失（这类 bug 已修，但改动涉及审核回调，**升级后必须重启后端**）。
> 想让自己的内容免审，需在后台「系统设置 → 文章 / 动态 / 评论配置」里显式关闭审核。

## 前端用法

| 输入位置 | 组件 | 交互 |
| :--- | :--- | :--- |
| 评论（含回复）、动态 | `components/EmojiEditor.vue` | 输入 `@` 自动弹出候选面板；↑/↓ 选择、回车确认、Esc 关闭 |
| 文章、独立页 | `components/MarkdownEditor.vue` | 工具栏 `@` 按钮弹出候选面板，点选插入到光标处 |

插入的都是**纯文本 `@昵称`**（不是链接）—— 用户在编辑器里看到的就是自己打的内容，
规范化发生在保存时。

面板组件 `components/MentionPicker.vue`；候选一次取全量（上限 500）后本地过滤，
避免每敲一个字打一次接口。

渲染侧：正文里的 `<a class="mention">` 由 `main.js` 全局拦截点击后走 SPA 跳转
（`v-html` 里的普通 `<a>` 直接点击会整页刷新）。文章 / 独立页的同类链接在
`utils/markdown.js` 的 `link_open` 规则里补上同一个 class。

## 新增接口与权限

| 接口 | 权限 | 说明 |
| :--- | :--- | :--- |
| `GET /api/mention/candidates` | `type=login` | 候选用户（仅"我关注的人"） |

写入没有独立接口 —— @ 是**保存内容时**由对应控制器调用 `model.Mention.Normalize()` 完成的，
调用点共四处：`app/api/controller/` 下的 `comment.go`、`moments.go`、`article.go`、`pages.go`。

> `app/model/auth-rules.go` 里已登记 `mention` 的 `candidates` 规则。**升级部署后需要重启一次后端**
> （规则种子在启动时同步进数据库），否则该接口会按未登记处理而返回 403。
