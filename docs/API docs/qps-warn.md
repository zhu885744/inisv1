## QPS告警管理 API

### 接口概述

QPS告警管理控制器，提供QPS告警记录的 CRUD 操作及数据统计功能。

**核心功能**：当系统检测到IP频繁请求超过阈值时，自动记录告警信息；当同一IP在设定时间窗口内累计告警次数达到封禁阈值时，**自动将该IP加入黑名单**。

---

| 状态码 | 含义 | 使用场景 |
| :--- | :--- | :--- |

### 特殊说明

#### 1. QPS告警机制

QPS警告由两个配置项控制，均在 `config` 表中通过 key 存储：

| 配置Key | 类型 | 说明 |
| :--- | :--- | :--- |
| `SYSTEM_QPS` | 基础配置 | 控制是否启用QPS限流，以及单接口/全局请求速度阈值 |
| `SYSTEM_QPS_BLOCK` | 封禁配置 | 控制时间窗口内触发多少次警告后自动封禁IP |

**SYSTEM_QPS 配置项**（value 为 true/false，json 中存储具体参数）：

```json
{
  "point": 120,   // 单接口限速：每秒最多请求数（默认值）
  "global": 600   // 全局限速：每秒最多请求数（默认值）
}
```

**限流实现**（`app/middleware/qps.go`）：

- 计数走缓存原子自增（`facade.Cache.Incr`），按「秒」分桶：每个 `scope + id + 秒` 一个键，
  语义是**每秒最多 `speed` 次**（`point` 与 `global` 一致，不再有「突发 + 补充速率」的令牌桶行为）；
- redis 驱动下多实例共享同一份计数，阈值不会随实例数放大；`file` / `ram` 驱动只在单实例内有效；
- 缓存故障时熔断 30 秒，期间直接放行（限流是保护性功能，不能因为缓存不可用把整站打成 429）；
- 超限返回 `{"code":429,"msg":"请求过于频繁！"}`，并异步写入 QPS 告警（受下方封禁配置约束）。

**SYSTEM_QPS_BLOCK 配置项**（value 为 true/false，json 中存储具体参数）：

```json
{
  "count": 200,       // 在时间窗口内累计警告次数阈值，达到后自动封禁（默认值）
  "second": "60 * 60" // 时间窗口（秒），支持表达式，即最近 N 秒内的警告次数
}
```

**超限去重**：同一 IP 每 **10 秒**只记一条告警、只参与一次封禁判定。
一次页面加载可能并发几十个请求，若每个被拒的请求都单独计数，正常访问一次就能把阈值击穿
（历史默认值 `count=3` 正是这样误封的）。去重后并发风暴只算「一次超限」。

**工作流程**：

```
用户请求过于频繁（超过QPS阈值）
    ↓
系统返回 429 错误（请求过于频繁）
    ↓
同一 IP 10 秒内只处理一次：未命中则直接结束
    ↓
向 qps_warn 表写入一条警告记录（记录IP、路径、User-Agent）
    ↓
窗口内超限次数 +1（计数保存在缓存，带 TTL；缓存不可用时回落数据库统计）
    ↓
次数 >= count 配置 → 自动将该IP加入 ip_black 黑名单，并清零计数
```

**阈值兜底**：`count` 小于 30 时按 30 处理。旧版本的默认值「1 小时 3 次」是配合进程内令牌桶
（100 次/秒补充）使用的，在按秒严格计数后会误封，服务启动时会把「仍是历史默认值」的配置
自动升级一次（`point` 15/60→120、`global` 50/200→600、`count` 3/30→200、窗口统一为 1 小时），
管理员手工改过的值不会被覆盖。

**手机 App / NAT 场景**：移动端上线后，同一出口 IP 会承载大量正常请求（通知轮询、NAT 共享
地址），按 IP 封禁很容易误伤整片用户。默认值已按此场景放大（去重后 200 次/小时，相当于
至少 33 分钟持续超限才会封禁）。如果仍然担心，建议把 `SYSTEM_QPS_BLOCK` 的 `value` 关掉，
只保留 QPS 限流（429）和 `security.qps_ban` 邮件告警，人工决定是否封禁。

#### 2. IP封禁等级升级逻辑

被自动封禁的IP会根据历史违规次数自动升级封禁等级：

| 违规次数 | 封禁等级 | 封禁时长 |
| :--- | :--- | :--- |
| 第 1 次 | 1 级 | 1 小时 |
| 第 2 次 | 2 级 | 24 小时 |
| 第 3 次 | 3 级 | 7 天 |
| 第 4 次及以上 | 永久 | 永久封禁 |

每次自动封禁时 `violation_count` 字段自动 +1。

**已在封禁期内不会再升级**：命中封禁逻辑时会先判断记录是否仍在生效期，生效期内直接返回，
避免「封禁期间的每次超限都升一级」一路升到永久封禁。封禁生效后窗口计数会清零，
解封后重新累计。

#### 3. 与 IP 白名单的关系

- 加入 `IpWhite` 白名单的 IP **不受 QPS 限制和自动封禁影响**
- 白名单IP即使触发了QPS警告，也不会被自动加入黑名单
- 推荐将可信的内部服务、测试IP加入白名单
- **本机与内网地址（回环、`10/8`、`172.16/12`、`192.168/16`、`100.64/10`、链路本地）自动放行**：
  这些地址通常来自同机 Nginx、容器或内网反代，一旦计入限流，所有访客会共享同一个配额

#### 4. 自动解封

- 系统后台协程每 **5 分钟** 自动检查所有黑名单记录
- 到期的临时封禁自动软删除（从黑名单中移除）
- 永久封禁需手动删除才能解封

#### 5. 缓存机制

- 查询接口支持缓存
- 缓存键：`[GET][qps-warn][column]`
- 数据更新后自动清除相关缓存

#### 6. 告警记录清理

- 每小时清理一次 **7 天前** 的 `qps_warn` 记录（真删除，分批 500 条）
- 多实例通过缓存锁保证同一时刻只有一个实例执行
- 告警表只增不减会随访问量无限增长，7 天足够事后定位问题

#### 7. 真实 IP 与可信代理

限流和封禁都依赖 `ClientIP`，取错会导致「所有访客共用一个 IP」而集体被封。配置项在
`config/app.toml`：

```toml
[app]
# 英文逗号分隔，支持 CIDR；默认只信任本机
trusted_proxies = "127.0.0.1,::1"
```

- 留空：不信任任何代理，直接取 `RemoteAddr`（客户端伪造的 XFF 会被忽略）
- 同机 Nginx：保持默认即可
- 使用 CDN / 跨机反代：必须把回源 IP 段加进来，否则拿到的是节点 IP，全部访客共享限流
- `*`：信任所有来源，**不推荐**（任何人都能伪造 XFF 绕过限流或陷害他人 IP）

#### 8. 封禁通知

封禁发生时通过**统一邮件通知**发送，场景 key 为 `security.qps_ban`（默认开启），在后台
「系统设置 → 邮件通知」里开关、配置管理员收件邮箱。正文包含 IP、封禁等级、时长、原因、
触发路径和 User-Agent。

早期预留的 `SYSTEM_QPS_NOTIFY`（邮件 / Webhook）从未实现，只有两条 TODO 日志，
已下线并从老库中自动删除；不要再往这个配置项写数据。
