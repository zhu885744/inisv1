# 用户拉黑 接口文档

## 接口概述

`user-blocks` 控制器提供**拉黑 / 解除拉黑 / 查询拉黑状态**能力。

拉黑的语义是**双向**的：一旦 A 拉黑 B，双方的内容都不会再出现在对方的聚合流与动态页里
（判定见 `app/model/user-blocks.go` 的 `BlockedUids` / `CanInteract`）。
但**列表接口只返回「我主动拉黑的人」**，不含「拉黑我的人」——避免把别人对你的态度暴露出来。

### 接口类型说明

| 接口类型 | 说明 |
| :--- | :--- |
| **读接口** | `mine`（我的拉黑列表）、`status`（是否已拉黑）—— 需登录（`type=login`） |
| **写接口** | `block`（拉黑）、`unblock`（解除拉黑）—— 需登录，且只能操作自己的拉黑关系 |
| **删除接口** | 无 —— DELETE 统一返回 405 |

---

## 状态码规范

| 状态码 | 说明 | 使用场景 |
| :--- | :--- | :--- |
| **200** | 请求成功 | 正常返回（业务码在 body 的 `code` 字段） |
| **400** | 请求错误 | 参数为空、不能拉黑自己、模型层失败 |
| **401** | 未授权 | 未登录（body 带 `"auth":"guest"`） |
| **403** | 无权限 | 试图拉黑系统管理员（`uid=1`） |
| **404** | 资源不存在 | 目标用户不存在 |
| **405** | 方法不允许 | method 不存在，或对 DELETE 调用 |

---

## 接口列表

### 1. 我的拉黑列表 [mine]

- **接口类型**: 业务接口
- **请求方式**: `GET`
- **请求地址**: `/api/user-blocks/mine`
- **说明**: 分页返回**我主动拉黑**的人，每条附被拉黑用户的公开信息

- **权限**: `type=login`

**请求参数**:

| 参数名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `page` | int | 否 | 页码，默认 1，上限 50 |
| `limit` | int | 否 | 每页条数，默认 20，上限 50 |

**成功响应** (200):

```json
{
    "code": 200,
    "msg": "查询成功！",
    "data": {
        "data": [
            {
                "id": 9,
                "uid": 7,
                "block_uid": 3,
                "reason": "骚扰",
                "create_time": 1731000000,
                "user": {
                    "id": 3,
                    "nickname": "小明",
                    "avatar": "https://...",
                    "description": "",
                    "title": null
                }
            }
        ],
        "count": 2,
        "page": 1
    }
}
```

> `user` 只含 `id / nickname / avatar / description / title` 五个公开字段（已做隐私清洗）；
> 用户已被删除时只剩 `{ "id": 3 }`。

### 2. 是否已拉黑某人 [status]

- **接口类型**: 业务接口
- **请求方式**: `GET`
- **请求地址**: `/api/user-blocks/status`
- **说明**: 查询「**我**是否拉黑了对方」，供前端按钮状态使用（**单向判定**）

- **权限**: `type=login`

**请求参数**:

| 参数名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `block_uid` | int | **是** | 目标用户ID；`<=0` 返回 400 |

**成功响应** (200):

```json
{ "code": 200, "msg": "查询成功！", "data": { "blocked": false } }
```

> ⚠️ 这是**单向**判定：`blocked=false` 不代表「对方也没拉黑我」。
> 内容过滤用的是**双向**判定，UI 文案不要写成「互不拉黑」。

---

### 3. 拉黑用户 [block]

- **接口类型**: 业务接口
- **请求方式**: `POST`
- **请求地址**: `/api/user-blocks/block`
- **说明**: 拉黑某人（**幂等**：重复拉黑不报错，也不会产生第二条记录）。

- **权限**: `type=login`

  同时会**解除双方关注关系**并清理聚合流缓存

**请求参数**:

| 参数名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `block_uid` | int | **是** | 被拉黑用户ID |
| `reason` | string | 否 | 拉黑原因（仅自己可见），超过 120 字符会截断 |

**成功响应** (200):

```json
{
    "code": 200,
    "msg": "已拉黑，对方的内容不会再出现在你的动态流里！",
    "data": { "block_uid": 3 }
}
```

**错误响应**:

| code | msg | 触发条件 |
| :--- | :--- | :--- |
| 401 | `请先登录！` | 未登录 |
| 400 | `block_uid 不能为空！` | `block_uid <= 0` |
| 400 | `不能拉黑自己！` | `block_uid == 自己` |
| 403 | `不能拉黑系统管理员！` | `block_uid == 1` |
| 404 | `用户不存在！` | 目标用户不存在 |
| 400 | `拉黑失败，请稍后重试！` | 唯一索引冲突等模型层失败（已兜底，不会把 MySQL 原文抛给前端） |

---

### 4. 解除拉黑 [unblock]

- **接口类型**: 业务接口
- **请求方式**: `PUT`
- **请求地址**: `/api/user-blocks/unblock`
- **说明**: 解除拉黑（**物理删除**，幂等：本就没拉黑也返回成功），并清理双方聚合流缓存

- **权限**: `type=login`

**请求参数**:

| 参数名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `block_uid` | int | **是** | 目标用户ID；`<=0` 返回 400 |

**成功响应** (200):

```json
{ "code": 200, "msg": "已解除拉黑！", "data": { "block_uid": 3 } }
```

> ⚠️ 解除拉黑**不会恢复**之前的关注关系（需要用户重新关注）。

---

本控制器不开放删除：

```json
{ "code": 405, "msg": "拉黑关系请用拉黑 / 解除拉黑接口，不支持该操作！", "data": null }
```

---

## 特殊说明

1. **HTTP 状态码恒为 200**，业务码在 body 的 `code`；
2. **未登记权限规则的方法会先被中间件拦成 401**：匿名调用 `DELETE /api/user-blocks/xxx`
   得到 401 而不是控制器的 405；
3. **拉黑会顺带解除关注**，且**不能拉黑系统管理员**（403）；
4. **`mine` 只返回我主动拉黑的人**，不含拉黑我的人；而内容过滤是双向的；
5. **拉黑 / 解除后立即生效**：聚合流的缓存 key 带了「拉黑集合指纹」（热门流）或 uid
   （关注流 / 推荐流），不会出现「拉黑后对方内容还在缓存里」的情况；
6. **整型参数是宽松转换**：`block_uid` 传字符串 `"3"` 也可用；传空 / 0 / 非数字一律得到
   `block_uid 不能为空！`（400），而不是类型错误；
7. **`unblock` 是物理删除，`report/cancel` 是软删除** —— 两者回收站语义不同，别混用。
