# Users 用户管理接口文档

## 接口概述

`users` 控制器用于管理系统用户数据，支持用户的 CRUD 操作、状态管理、封禁管理、小黑屋公示、用户申诉、邮箱/手机号修改及账户注销功能。所有接口均支持缓存优化和权限控制。

### 接口类型说明

| 接口类型 | 说明 |
| :--- | :--- |
| **基础接口** | one、all、rand、count、sum、min、max、column、remove、delete、clear、restore、save、create、update |
| **特殊接口** | email（修改邮箱）、phone（修改手机号）、status（修改状态）、ban（封禁用户）、unban（解封用户）、appeal-handle（处理申诉）、blackroom（小黑屋公示）、appeal（用户申诉）、appeal-public（公开申诉）、destroy（注销账户） |

---

## 状态码规范

| 状态码 | 说明 | 使用场景 |
| :--- | :--- | :--- |
| **200** | 请求成功 | 获取数据成功、操作成功 |
| **201** | 创建成功 | 新增数据成功、验证码发送成功 |
| **202** | 接受请求 | 请求已接受（无实际功能） |
| **204** | 无内容 | 查询无数据、无可操作数据 |
| **400** | 请求错误 | 参数校验失败、操作失败 |
| **401** | 未授权 | 用户未登录 |
| **403** | 无权限 | 无操作权限 |
| **405** | 方法不允许 | 请求方法错误或方法名错误 |
| **500** | 服务器错误 | 系统内部错误 |

    "code": 200,
    "msg": "数据请求成功！",
    "data": {
        "data": [
            {
                "id": 1,
                "uid": 100,
                "ban_type": 31,
                "reason": "发布违规内容",
                "duration": 7,
                "ban_time": 1700000000,
                "expires_at": 1700604800,
                "violation_num": 1,
                "status": 0,
                "result": {
                    "user": {
                        "id": 100,
                        "nickname": "张*三",
                        "avatar": "..."
                    },
                    "operator": {
                        "id": 1,
                        "nickname": "管理员",
                        "avatar": "..."
                    },

                        {"bit": 1, "name": "限制登录"},
                        {"bit": 2, "name": "限制发表内容"}

**响应字段说明**:

| 字段 | 类型 | 说明 |

| `ban_type` | int | 封禁类型位掩码（1=限制登录，2=限制发表，4=限制评论，8=限制上传，16=限制互动，31=全部） |

#### 2.3 用户申诉 [特殊接口]

- **路径**: `/api/users/appeal`
- **方法**: `POST`
- **权限类型**: `login`（需登录）
- **描述**: 被封禁用户提交申诉，更新封禁记录状态为"申诉中"

**请求参数**:

| 参数名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `record_id` | int | **是** | 封禁记录ID |
| `content` | string | **是** | 申诉内容 |

**成功响应** (200):
```json
{
    "code": 200,
    "msg": "申诉已提交，请耐心等待管理员审核！",
    "data": {
        "id": 5
    }
}
```

**错误响应**:
| code | msg | 说明 |
| :--- | :--- | :--- |
| 400 | 当前封禁状态不允许申诉！ | 只有生效中的封禁才能申诉 |
| 400 | record_id 不能为空！ | 缺少必填参数 |
| 400 | 申诉内容 不能为空！ | 申诉内容为空 |
| 403 | 无权操作此封禁记录！ | 只能申诉自己的封禁记录 |
| 403 | 该封禁为永久封禁且违规次数已达上限，禁止申诉！ | 五次及以上违规永久封禁不可申诉 |
| 404 | 封禁记录不存在！ | record_id 无效 |

**权限说明**:
- 用户只能申诉自己的封禁记录
- 只有状态为"生效中"（status=0）的封禁才能提交申诉
- 提交后封禁记录状态变为"申诉中"（status=3）

#### 2.4 公开申诉 [特殊接口]

- **路径**: `/api/users/appeal-public`
- **方法**: `POST`
- **权限类型**: `common`（公开访问，无需登录）
- **描述**: 被封禁用户无需登录即可提交申诉，通过账号与封禁记录的关联关系验证身份

**请求参数**:

| 参数名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `record_id` | int | **是** | 封禁记录ID（可在小黑屋公示页找到） |
| `account` | string | **是** | 被封禁用户的登录账号 |
| `content` | string | **是** | 申诉内容 |

**成功响应** (200):
```json
{
    "code": 200,
    "msg": "申诉已提交，请耐心等待管理员审核！",
    "data": { "id": 5 }
}
```

**错误响应**:
| code | msg | 说明 |
| :--- | :--- | :--- |
| 403 | 账号与封禁记录不匹配！ | account 不属于该封禁记录的 uid |
| 403 | 该封禁为永久封禁且违规次数已达上限，禁止申诉！ | 五次及以上违规不可申诉 |
| 400 | 当前封禁状态不允许申诉！ | 只有生效中的封禁才能申诉 |
| 404 | 封禁记录不存在！ | record_id 无效 |

**权限说明**:
- 公开接口，无需登录即可调用
- 通过 `account` 参数匹配封禁记录的 `uid` 来验证身份
- 提交后封禁记录状态变为"申诉中"（status=3）

### 5. 封禁系统

#### 5.1 封禁类型对照表

封禁类型采用**位掩码**设计，多个限制可通过位运算组合（如 `3` = 限制登录 + 限制发表内容）：

| 位 | 十进制值 | 常量名 | 限制内容 | 效果说明 |
| :--- | :--- | :--- | :--- | :--- |
| bit 0 | **1** | `限制登录` | 禁止登录 | 无法登录系统，JWT 中间件和登录接口均拦截 |
| bit 1 | **2** | `限制发表内容` | 禁止发表文章/动态 | 拦截 `POST/PUT /api/article/*` 和 `/api/moments/*` |
| bit 2 | **4** | `限制评论` | 禁止评论 | 拦截 `POST /api/comment/*` |
| bit 3 | **8** | `限制上传` | 禁止上传附件 | 拦截 `POST /api/attachment/upload` |
| bit 4 | **16** | `限制互动` | 禁止点赞/收藏/关注 | 拦截 `/api/user-likes/*`、`/api/user-collects/*`、`/api/user-follows/*` |
| 全部 | **31** | `全部封禁` | 以上全部 | 等同于 bit 0-4 全部置位 |

> **前端对接建议**: 可直接将十进制值传给 `ban_type` 参数。例如只限制登录和评论则传 `1+4=5`，全封禁传 `31`。

#### 5.2 限制中间件与路由映射

细粒度权限由 `Restriction` 中间件（`app/api/middleware/restriction.go`）统一拦截。中间件根据请求的路由自动匹配所需的权限位，拦截受限用户的请求并返回 403。

| 权限位 | 十进制 | 匹配路由规则 |
| :--- | :--- | :--- |
| 限制登录 | 1 | JWT 中间件 + `POST /api/comm/login` 登录接口内部检查 |
| 限制发表内容 | 2 | `POST|PUT /api/article/*`、`POST|PUT /api/moments/*` |
| 限制评论 | 4 | `POST|PUT /api/comment/*` |
| 限制上传 | 8 | `POST /api/attachment/upload` |
| 限制互动 | 16 | `POST|PUT /api/user-likes/*`、`POST|PUT /api/user-collects/*`、`POST|PUT /api/user-follows/*` |

> **开发说明**: 中间件通过 `routeRestrictionMap` 路由表做前缀匹配。新增受限接口时，需要在 `restriction.go` 中注册对应路由映射。Controller 内部也可调用 `middleware.CheckUserRestriction(ctx, model.BanTypeXxx)` 进行额外检查。

**受限用户的错误响应** (403):
```json
{
    "code": 403,
    "msg": "您当前的账号操作受到限制，如有疑问请提交申诉！",
    "data": null
}
```

#### 5.3 自动解封逻辑

后台定时任务（`app/timer/ban.go`）**每 60 秒**执行一次自动解封检查，具体流程如下：

1. **扫描到期记录**: 查询 `inis_user_ban_records` 表中满足 `expires_at > 0 AND expires_at <= 当前时间 AND status = 0（生效中）` 的所有记录
2. **更新封禁记录**: 将到期记录的状态从 `0（生效中）` 更新为 `1（已解封）`，并记录 `unban_time`（实际解封时间）
3. **恢复用户状态**: 将 `inis_users` 表中对应用户的 `current_ban_id` 重置为 `0`，`restrictions` 重置为 `0`（解除所有限制）
4. **清除缓存**: 删除用户缓存 `user[{uid}]`，下次请求时重新查询数据库获取最新状态
5. **记录审计日志**: 通过 `facade.Log.Info` 记录解封事件（含用户ID、记录ID、封禁时长）

> **注意事项**:
> - 自动解封**不会**清除用户的 `ban_count`（累计封禁次数），该字段用于自动梯度计算
> - 解封后用户可立即正常登录和操作，无需额外等待
> - 若定时任务执行失败（如数据库异常），会记录错误日志并跳过当前记录，下个周期重试
> - 永久封禁（`duration=0`）的记录 `expires_at=0`，不会被自动解封扫描到

#### 5.4 申诉状态与封禁状态的关系

| 申诉状态 | 封禁记录 status | 用户 restrictions | 用户 current_ban_id | 用户实际状态 |
| :--- | :--- | :--- | :--- | :--- |
| 提交申诉 | 3（申诉中） | 保持封禁时的值 | 保持原值 | **仍然受限**，申诉期间限制不解除 |
| 申诉通过 | 4（申诉通过） | 重置为 0 | 重置为 0 | **解除限制**，恢复正常使用 |
| 申诉驳回 | 5（申诉驳回） | 保持封禁时的值 | 保持原值 | **仍然受限**，继续执行原封禁 |

> **关键规则**: 
> - 申诉提交后**不会自动解除封禁**，用户仍处于受限状态
> - 仅当管理员审核通过后，才会执行解封操作（`restrictions=0`, `current_ban_id=0`）
> - 申诉驳回后封禁继续生效，到期后仍会被自动解封任务正常解除
> - 管理员也可在申诉期间直接手动解封（此时 status 变为 2 已撤销）

#### 5.5 封禁状态流转

```
                     ┌──────────────┐
                     │  生效中 (0)   │ ← 管理员封禁
                     └──┬───┬───┬──┘
         到期自动        │   │   │  用户申诉
     ┌───────┘    管理员撤销│   │   └──────────┐
     ▼                    ▼   ▼              ▼
┌─────────┐          ┌─────────┐      ┌──────────┐
│已解封(1)│          │已撤销(2) │      │ 申诉中(3) │
└─────────┘          └─────────┘      └──┬───┬───┘
                                  管理员通过│   │驳回
                                      ┌───┘   └────┐
                                      ▼            ▼
                              ┌──────────┐   ┌──────────┐
                              │申诉通过(4)│   │申诉驳回(5)│
                              │(解除限制) │   │(继续封禁) │
                              └──────────┘   └──────────┘

只有 status=0（生效中）时用户才处于受限状态。
status 变为 1/2/4 时，用户 restrictions 清 0，current_ban_id 清 0，恢复正常。
status=3/5 时用户仍然受限，封禁继续生效。
violation_num >= 5 的永久封禁无法提交申诉。
```

#### 5.6 其他说明
- 封禁后自动清除用户缓存 (`user[{uid}]`) 和 Token 前缀缓存，强制用户下线
- 登录时检测封禁状态，包含限制登录位（bit 0）的用户将被拒绝登录并提示剩余天数或永久封禁原因
- 自动梯度封禁：首次 1 天 → 二次 7 天 → 三次 15 天 → 四次 30 天 → 五次及以上永久且禁止申诉
- 管理员手动解封后封禁记录状态变更为"已撤销"（status=2），区别于到期自动解封的"已解封"（status=1）
- 所有封禁/解封/申诉操作均记录操作人 IP、User-Agent 和操作时间到审计日志
