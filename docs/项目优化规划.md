# inis CMS 项目后期优化规划

> **本文档定位**：区别于《项目后期发展规划.md》（面向功能新增），本文档聚焦于**在不新增业务功能的前提下，对现有系统进行优化调整**，以提升系统的安全性、正确性、性能与可维护性。
>
> **核心原则**：
> 1. 不新增业务模块、不新增对外 API、不改变现有数据表业务语义；
> 2. 只做「修 bug、堵漏洞、提性能、减重复、立规范」五类优化；
> 3. 优化以「可灰度、可回滚、低风险」为准则，优先处理高风险项；
> 4. 优化顺序：安全 > 正确性 > 性能 > 可维护性。

---

## 一、现状综述

基于对 `app/`（139 个 Go 文件）、`config/`、`main.go` 的全局代码审查，当前系统整体架构清晰、分层合理（controller / validator / model / facade / middleware / timer / socket），功能覆盖完整。但存在以下共性问题：

| 问题领域 | 总体评价 |
|----------|----------|
| 安全性 | 存在硬编码密钥、SQL 拼接注入点、路径遍历、密钥文件权限过宽等**高危漏洞**，需优先修复 |
| 事务与并发 | 多处「异步 goroutine + 脱离事务」的删除/更新操作，存在数据不一致与竞态 |
| 错误处理 | 大量 `_, err :=` 忽略错误，查询失败与「无数据」语义混淆 |
| 参数校验 | validator 规则过少，关键字段依赖手工校验且覆盖不全 |
| 代码重复 | Article / Comment / Users 三控制器存在大量逐字重复的样板方法 |
| 类型安全 | 大量 `any` / `interface{}` + 反射调用，丧失编译期检查 |
| 性能 | 图片动态处理无缓存、权限判断实时查库、部分高频查询缺索引 |
| 工程规范 | 调试代码（`fmt.Println`）残留、命名不一致、死代码未清理 |

> 详细问题清单见配套文档《代码优化清单.md》，本文档聚焦于「做什么、怎么做、按什么顺序做」。

---

## 二、优化优先级分级

| 级别 | 定义 | 触发条件 | 目标周期 |
|------|------|----------|----------|
| **P0（紧急）** | 安全漏洞，可被外部直接利用 | SQL 注入、路径遍历、硬编码密钥、密钥泄露 | 立即处理 |
| **P1（高）** | 正确性问题，会导致数据不一致或功能异常 | 事务缺失、并发竞态、错误静默 | 1 个迭代内 |
| **P2（中）** | 性能与体验问题 | 缺索引、无缓存热点、goroutine 堆积 | 1-2 个迭代 |
| **P3（低）** | 可维护性与规范问题 | 重复代码、死代码、命名、注释 | 持续进行 |

---

## 三、分阶段优化路线

```
Phase A（安全加固）  →  Phase B（正确性修复）  →  Phase C（性能优化）  →  Phase D（工程治理）
    P0 漏洞清零            P1 事务/并发修复            P2 缓存/索引/慢查询       P3 去重/规范/死代码
```

### Phase A：安全加固（P0）

**目标**：清除所有可被外部利用的安全漏洞。

| 序号 | 优化项 | 涉及文件 | 说明 |
|------|--------|----------|------|
| A1 | 密钥外置化 | `app/facade/const.go` | 将 `Token = "(unti.io)"` 移出代码，改为从配置文件读取并支持环境变量覆盖 |
| A2 | 修复 SQL 拼接注入 | `app/facade/mysql.go` | `ILike`、`Where`、`WhereIn`、`Sum/Max/Min` 中的字段名/值拼接改为 GORM 参数绑定或字段名白名单 |
| A3 | 修复路径遍历 | `config/app.go`、`app/facade/storage.go` | 静态文件读取与存储删除增加路径规范化（`filepath.Clean` + 前缀校验），禁止 `../` 逃逸 |
| A4 | 密钥文件权限收紧 | `app/facade/crypt.go` | `crypt.toml` 写入权限由 `0755` 改为 `0600` |
| A5 | JWT 密钥生成强化 | `app/facade/crypt.go` | 用 `crypto/rand` 生成随机字节替代 `md5(uuid+时间戳)` |
| A6 | 移除密钥日志泄露 | `app/facade/crypt.go` | 热更新日志不再打印 `jwt.key` 明文 |
| A7 | 硬编码 Token 治理 | `app/middleware/token.go` | `"0147."` 改为配置项，比较改用 `subtle.ConstantTimeCompare` |
| A8 | 密码哈希审计 | 全局 | 审计 `utils.Hash.Sum32` 是否加盐，必要时迁移至 bcrypt/argon2 |

**验收标准**：P0 漏洞全部关闭，静态扫描（gosec / govulncheck）无高危项。

---

### Phase B：正确性修复（P1）

**目标**：消除「异步脱离事务」「并发竞态」「错误静默」导致的数据不一致。

| 序号 | 优化项 | 涉及文件 | 说明 |
|------|--------|----------|------|
| B1 | 封禁删除内容同步化 | `app/api/controller/users.go` `ban` | 删除文章/评论等操作移入事务或同步执行并检查错误 |
| B2 | 注销流程事务化 | `app/model/users.go` `Destroy` | 关联数据清空改为同步 + 事务 + 错误上抛，移除裸 goroutine |
| B3 | 修复 AfterSave 异步更新竞态 | `app/model/users.go` `AfterSave` | 头像域名替换改为同步处理，避免复用事务 `tx` 与数据竞争 |
| B4 | 经验值原子发放 | `app/model/exp.go` `Add` | 「流水创建 + 用户 exp 自增」包入事务或使用原子 SQL |
| B5 | 频控计数原子化 | `app/api/controller/users.go` | 发码/申诉频控由「读-改-写」改为 Redis INCR / DB 原子自增 |
| B6 | 邮件通知重试治理 | `app/api/controller/comment.go` | 分钟级 `time.Sleep` 重试改为带超时/取消的消息队列或有限重试 |
| B7 | 错误处理补全 | 全局 | 系统性补齐 `_, err :=` 的 error 处理，至少记录日志；查询类方法区分「无数据」与「查询失败」 |

**验收标准**：注销/封禁全流程在异常注入测试下数据一致；并发压测下频控计数不丢失。

---

### Phase C：性能优化（P2）

**目标**：降低热点查询耗时，减少重复计算与资源浪费。

| 序号 | 优化项 | 涉及文件 | 说明 |
|------|--------|----------|------|
| C1 | 图片处理加缓存 | `config/app.go` `handleImageFile` | 动态裁剪/缩放结果缓存到内存或文件，避免每次请求重新读盘+编码 |
| C2 | 权限判断加缓存 | `app/api/controller/base.go` `meta.root` | `AuthGroup` 实时查库改为缓存 + 变更时失效 |
| C3 | 索引落地 | 见 `docs/database-index.md` | 确认核心表（article/comment/user/config/auth_*）索引已创建 |
| C4 | 缓存键规范化 | `app/api/controller/*.go` | 统一缓存键前缀格式，避免清理遗漏导致脏缓存 |
| C5 | 慢查询排查 | 全局 | 开启慢查询日志，对 `LIKE '%...%'`（权限组 uids）等低效查询评估改造 |

**验收标准**：核心列表接口 P99 响应时间下降，缓存命中率 ≥ 90%（见 database-index.md 监控建议）。

---

### Phase D：工程治理（P3）

**目标**：降低维护成本，提升代码质量与团队协作效率。

| 序号 | 优化项 | 涉及文件 | 说明 |
|------|--------|----------|------|
| D1 | 抽取公共基类 | `article.go`/`comment.go`/`users.go` | 收敛 `buildQuery`/`getFromCache`/`count`/`sum` 等重复样板方法 |
| D2 | 脱敏/发码逻辑复用 | 多个 controller | 提取统一的脱敏 helper 与「发码 + 频控」helper |
| D3 | 清理死代码 | `app/model/comment.go`、`app/api/middleware/ip-black.go` | 删除无引用的旧方法 `author/article/page`、`IsIpBanned` 等 |
| D4 | 收敛 any/反射 | `app/api/controller/base.go` | 逐步用强类型替代 `map[string]any` + 反射动态调用 |
| D5 | 清理调试输出 | `test.go`、`OAuth.go`、`serialize.go` | 移除残留 `fmt.Println`，统一走 `facade.Log` |
| D6 | 拆分超长文件 | `users.go`（2000+ 行） | 按职责拆分 controller 业务逻辑 |
| D7 | 修复热更新阻塞 | `main.go` `watch` | 解决 `run()` 内 `select{}` 阻塞导致的配置热更新失效 |

**验收标准**：重复代码明显收敛，`golangci-lint` 关键告警清零，`go vet` 通过。

## 四、风险与注意事项

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 密码哈希算法迁移 | 存量用户无法登录 | 采用「旧算法校验通过后自动重哈希」的平滑迁移，不强制一次性切换 |
| SQL 拼接改造 | 影响现有 `ILike`/`Where` 调用语义 | 保持函数签名不变，仅内部改为参数绑定，回归测试全量覆盖 |
| 事务改造 | 阻塞时间变长 | 缩小事务边界，只包必要语句；删除操作同步化前评估数据量 |
| 缓存新增 | 引入脏数据 | 严格设计失效策略，删除/更新后主动清缓存 |
| 异步转同步 | 响应变慢 | 对耗时操作（邮件等）保留异步但补上失败告警与重试，不回归为裸 goroutine |

---

## 五、实施建议

1. **P0 先行**：Phase A 的安全漏洞应独立快速修复，不与其他改动混排，便于单独上线与回滚。
2. **小步提交**：每个优化项单独提交，提交信息注明对应编号（如 `fix(A2): 修复 ILike SQL 拼接注入`）。
3. **回归保障**：当前项目缺少单元测试，建议在 Phase B/C 过程中为「注销/封禁/发码/权限」等核心链路补最小测试集，防止优化引入回归。
4. **工具引入（可选）**：可引入 `gosec`、`govulncheck`、`golangci-lint` 作为 CI 门禁，持续拦截回归。

---

## 六、与功能规划的衔接

本文档所列优化项与《项目后期发展规划.md》的功能规划互不冲突：
- 优化先行，为后续功能扩展（积分、勋章、消息中心等）打好安全与稳定性底座；
- 功能规划中「积分/余额并发安全」「WebSocket 消息不丢失」等风险点，已在本规划 Phase B 的并发治理中提前铺垫。
