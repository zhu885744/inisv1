## Socket 系统状态推送安全修复
背景：核对 `app/socket/controller` 代码时发现系统状态（每秒推送的 status）会推送给所有客户端，存在信息泄露。

修复内容（方案 B：系统状态只推管理员，非管理员完全不推）：
- `status.go` `pushStatusToClients`：改为只构造完整版消息（`admin_only:true`）并仅推送一条给 `Hub.notice`，非管理员不再收到任何 status。
- `status.go`：删除 `sanitizeStatus` 脱敏函数（已无引用，死代码）。
- `index.go` `hub.run` 的 `case status := <-hub.status:` 防御分支：由「脱敏后 broadcast 全员」改为「`broadcastToAdmin` 仅推管理员」，防止未来误用泄露。
- `index.go` `hub.run` notice 分支：拆分 `status`（仅管理员）与 `broadcast`/空 type（全员 `hub.broadcast`，含管理员），修复了客户端广播只发非管理员的语义 bug；并删除 `broadcastToNonAdmin` 死代码。

机制链路：`middleware/app.go` 里 `isAdmin(uid)`（root 权限组且含 `all`）→ `ctx.Set("is_admin", true)` → `index.go` Connect 时 `client.isAdmin = ctx.GetBool("is_admin")` → notice 分支里 `status` 走 `broadcastToAdmin`。

编译验证：`go build ./app/socket/...` 通过（两次修改后均通过）。

最终行为：
- 系统状态 `status`：仅管理员收到完整版；普通用户/访客完全收不到。
- 客户端广播 `broadcast`：全员可见（含管理员）。
- 在线状态 `broadcastStatus`（`online_users` 列表）：全员可见——产品要求保留，未改动。

## 跨域 WebSocket 身份认证修复（前后端分离）
背景：前后端分离（不同域名），WebSocket 握手跨站无法携带 Cookie（前端 axios `withCredentials:false`，HTTP 靠 Authorization header 手动带 token；但浏览器原生 WebSocket 不能设 header），导致后端 Jwt() 拿不到 token，登录用户被当成访客（uid=0 → isAdmin=false），进而收不到「只推管理员」的系统状态、在线列表显示成「访客」。

方案：连接后前端主动发 auth 消息，后端重新鉴权升级身份（不把 token 放 URL query）。

后端：
- `model/auth-group.go` 新增 `IsRootAdmin(uid)`（root=1 权限组 + uids 含 uid + rules 含 all），提取超级管理员判断。
- `socket/middleware/app.go` `isAdmin` 改为调用 `model.IsRootAdmin`（消除重复，删 strings/facade/utils import）。
- `socket/controller/serialize.go`：新增 `clientUpgrade` struct + `hub.upgrade` channel；`ValidateMessage` allowedTypes 加 `auth`。
- `socket/controller/index.go`：read() 识别 `auth` 消息 → `handleAuth`（`facade.Jwt().Parse(token)` → 查用户 → `utils.Hash.Sum32(password) != jwt.Data["hash"]` 校验 → 发 upgrade 请求）；hub.run 新增 `case up := <-hub.upgrade:` 更新 `client.username/isAdmin` 并 `broadcastStatus()`。
- 注意：升级仅更新 username/isAdmin，不动 `info.ID`（client_id 保持 guest_xxx），避免与 read goroutine 并发读写 info.ID 产生 race。

前端：
- `thems/src/composables/useSocket.js` onopen 后从 Cookie 读 token（`globalThis?.inis?.token_name || VITE_TOKEN_NAME || INIS_LOGIN_TOKEN`）发 `{type:'auth', token}`。

验证：`go build ./app/...` 通过。

## 通知过期自动清理
需求：通知记录只增不减，无自动清理，需定时清理。确认的设计点：只删「已读的 N 天前」、天数可配置、广播通知一起删。

实现：
- `model/notification.go` 新增 `CleanExpired(days)`：事务内删除已读个人通知（`uid!=0 AND is_read=1 AND create_time<阈值`）+ 过期广播通知（`uid=0`，先查 id 再连带删 `notification_read` 状态，再删本体，`Unscoped()` 物理删除）；`InitNotification` 补 `idx_notifications_create_time` 索引。
- `app/timer/notification.go`（新文件）：`NotificationStruct`，`Timer.Every(1).Day().At("04:00:00")` 调用 `CleanExpired`，天数从 `facade.AppToml.Get("notification.retention_days", 30)` 读。
- `app/timer/run.go`：注册 `Notification.Run()`。
- `facade/template.go`：TempApp 加 `[notification] retention_days = 30` 配置段（注意：模板里 socket 段配置项名是 `enable_ip_ban`，非 `ip_ban_enabled`）。

验证：`go build ./app/...` 通过。

## 通知配置权限规则补漏
问题：admin 改通知天数报「通知配置获取失败」，根因是权限规则表（auth-rules）缺 `/api/toml/notification` 规则，`Rule()` 中间件 403 拦截（管理员 `all` 权限展开的是表里已有规则，表里没有就放行不了）。

修复：`model/auth-rules.go` 的 `createAuthRules()` 中 `batch["toml"]` 的 GET 加 `path=notification&name=获取通知配置`、PUT 加 `path=notification&name=修改通知配置`。

生效：安装时 `mysql.migrate=true`，`model/base.go` init() 每次启动 `go InitTable()` → `InitAuthRules`（saveAuthRules 按 hash 幂等去重）→ 重启后自动补规则。

教训：新增 API 方法时，除了 controller 的 allow map，还要同步 `createAuthRules()` 的 batch 规则，否则被权限中间件拦截。
